# Fixes to the flow typing compiler

These are fixes for the problems in the reference compiler (the Rust sources generated by
`create_files.py` into `flow-typing-compiler/`) that are listed in §7 of
`COMPILER_COMPARISON.md`. Each one makes the compiler follow the `λF` typing rules
of the paper, as formalised in `RequestProject/FlowTyping/LambdaF.lean`.

* `flow-typing-compiler.patch` is the change, as a diff against the **original** generated sources
  (only `src/infer.rs` and `src/core.rs` change).
* `create_files.py` in the project root has been updated: it now generates the fixed
  `src/infer.rs` and `src/core.rs`. All other files are byte-for-byte the same as before. To
  apply the patch by hand instead, generate the original sources from the previous version of
  `create_files.py` and run `patch -p1 < flow-typing-compiler.patch` inside `flow-typing-compiler/`.
* `regressions.fl` has the test programs in the compiler's surface syntax.
* `harness/` is a small Rust crate that runs those programs through the compiler's real
  renaming, type-checking and translation passes (`rename.rs`, `infer.rs`, `core.rs`).
  The lexer and parser need crates from crates.io, which could not be downloaded here, so the
  harness writes each program directly as a parsed syntax tree instead.
  Run it with `python3 create_files.py && cd compiler-fixes/harness && cargo run`.

## What was fixed

| # | Problem (before) | Fix | Paper rule |
|---|---|---|---|
| 1a | `~(x, x)` was accepted and translated to ill-typed Haskell `((x, ()), …)` | `infer_lens`, tuple case: a variable may occur in only one component of a lens tuple. | `~⊗-I` splits the context |
| 1b | In `case ~u of …` and `let p = ~u in …`, the body could use the variables of `u`. `case ~x of y -> dup ~x` was translated to `dup ()`, and the `let` form crashed. | `infer_expr`, `Let` and `Case` cases: new check `check_scrutinee_split` rejects a body that mentions a variable of the lens scrutinee. | `~Let`, `~⊗-E`, `~⊕-E` split the context |
| 2 | `\~y -> ~x` (with `x` captured) was accepted. The output contained an unsolved type variable `?7`. | `infer_expr`, `Lambda` case: every variable that a lambda (plain or flow) captures must be dead at the end of its body. | `⊸-I`, `~⊸-I`: captured context ends as `Γ₂†` |
| 3 | A function `A ⊸ B/B'` applied to a plain argument and used as a lens was translated to `(ab, Γ₃)`, with `ares ()`. That is ill-typed. | `translate_lens`, `App` with a plain argument: it now builds `(ab, \bp -> ares bp; Γ₃)`, which has type `B ⊗ (B' ⊸ Γ₃°)`. | lens translation of `⊸-E` (§C) |
| 4a | `let p = ~u in t` passed the checker but crashed the translator (`out_of_scope!()`). | `translate_expr`, `Let` with a lens value: it is translated as the one-branch `case ~u of p -> t`. That case already had a translation. | `~Let`, `~⊗-E` |
| 4b | Literal lenses such as `inc ~3` passed the checker but crashed the translator. | `infer_lens`, `Literal` case: now a type error. The paper has no rule for them. | — |

## How the fixes were checked

The harness has 15 tests and all of them pass with the fixed sources. With the original sources, 6 of them fail: 1a, 1b
(`case` and `let`), 2, 4a and 4b. The program for 3 typechecks in both versions, so its test passes
either way; the before-and-after Haskell output for it is in the table above.

* **Regressions.** Programs from `examples.fl` still compile, and their translations are the same as in the shipped
  `flow/Examples.hs`. The programs checked are `inc`, `fst`, `incFst`, `swap`, `swapPair`, `united`, `idl`, `fcomp`,
  `join`, `funcurry`, `map`, `unmap`, `over`, `length`, `fileWords`, `avg`, `pop`, `push`,
  `split`, `usingFile`, `onZero` and `main`.
* **`badFileUsage`.** This program is commented out in `examples.fl` because it should not compile, and it is
  still rejected (now by the type checker, rule 2).

Not done here: building the real compiler with its parser, and compiling the generated Haskell
with GHC. Neither crates.io nor GHC was available. The Haskell outputs quoted above were checked by
reading them.

The Lean side has a theorem for each rule that the type-checker fixes enforce. Each one shows that the
corresponding program cannot be typed in `λF` (`RequestProject/FlowTyping/CompilerExamples.lean`):
`LensTy.not_pair_same_var` (1a), `LinTy.not_letInLens_reuse_var` and
`LinTy.not_caseLens_reuse_var` (1b), and `LinTy.not_lamSlash_capture_lens` (2).
